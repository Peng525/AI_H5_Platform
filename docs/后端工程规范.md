# 后端工程规范：解耦 · 健壮性 · 异常防护

> 对应 Cursor Rule：`.cursor/rules/backend-engineering.mdc`（执行计划时创建）  
> 适用于 `backend/` 下所有新增与改造代码。

## 1. 分层解耦（必须）

- **API 层**（`app/api/`）：只做路由、参数校验、鉴权依赖注入、HTTP 状态码映射；**禁止**直接写 SQL、支付 SDK 调用或大段业务逻辑。
- **服务层**（`app/services/`）：承载业务规则与编排；通过函数/类接口对外暴露，不依赖 FastAPI 的 `Request`/`Response`（webhook 验签可传入原始 body + headers 字典）。
- **依赖层**（`app/deps/`）：鉴权、项目归属、可选用户等横切关注点；API 通过 `Depends(...)` 复用，避免在每个端点重复校验。
- **数据层**（`models.py` + `database.py`）：模型与迁移；复杂查询可抽 `repositories/`（按需），避免 API 内联多表逻辑。
- **集成层**（如 `services/payment/`、`services/oauth/`）：第三方 SDK/HTTP 封装为独立模块，实现统一抽象（如 `PaymentProvider`），便于 mock 与切换渠道。
- **禁止** API ↔ 服务 ↔ 集成之间的循环依赖；共享类型放 `schemas.py` 或 `services/*/types.py`。

## 2. 健壮性（必须）

- 所有外部输入（JSON body、query、webhook payload）经 **Pydantic schema** 校验后再进入服务层。
- 数据库写操作放在明确的 **事务边界**内；多步更新（下单 + 改会员 + 写日志）要么全成功要么全回滚。
- 支付回调、OAuth 回调必须 **幂等**：同一 `trade_no` / `notify_id` 重复通知不得重复扣款或重复开通权益。
- 配置缺失（未配置微信/支付宝密钥）时，相关 API 返回 **503 或 400 + 明确中文提示**，不得 silent fail 或 500 裸奔。
- 禁止吞掉异常后返回假成功；`demo` 渠道与真实渠道行为差异须在服务层显式分支，不散落在多处。

## 3. 异常防护（必须）

- **自定义业务异常**（如 `QuotaExceeded`、`ProjectNotFound`、`PaymentVerifyError`）在服务层抛出；API 层统一映射为合适的 HTTP 状态与 `detail` 文案。
- **第三方调用**（LLM、支付、微信 OAuth）必须捕获超时、网络错误、验签失败，记录日志后转为对用户友好的错误，**不**把堆栈或密钥信息返回客户端。
- **JSON 解析**（`settings_json`、`canvas_json`、`bullets_json`）使用 try/except 或 validator，损坏数据降级为默认值并可选打 warning 日志，避免整请求 500。
- **鉴权失败**：401（未登录）与 403（无权限）区分；资源不存在用 404，避免通过响应差异泄露他人资源是否存在（项目归属校验统一策略）。
- 关键路径（支付回调、退款、配额扣减）写 **结构化日志**（order_id、user_id、channel、result），便于对账与排障。
- 不在 bare `except:` 中捕获；捕获后若需继续抛出，使用 `raise ... from exc` 保留链。

## 4. 实施检查清单（每次后端 PR 自检）

- [ ] 新逻辑是否在服务层而非 API 层？
- [ ] 是否新增/复用了 deps，避免复制粘贴鉴权代码？
- [ ] 外部依赖失败是否有明确异常类型与用户可读提示？
- [ ] 写操作是否幂等或具备防重入保护？
- [ ] 是否误将 `.env` 密钥、第三方原始错误堆栈返回给前端？
