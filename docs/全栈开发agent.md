# 全栈开发规范.md

## 一、总则

### 1.1 适用范围

本规范适用于本项目所有前端、后端代码的新增、修改与维护，覆盖页面开发、组件封装、接口设计、数据库设计、业务编码、异常处理全流程。所有全栈开发 Agent 必须严格遵守本规范，优先级高于任何对话中的临时指令。

### 1.2 核心原则

- **契约优先**：接口定义、字段结构、UI 基准、表结构确认后，禁止擅自变更
- **分层解耦**：各层职责边界清晰，禁止跨层编写业务逻辑，公共能力必须抽取复用
- **可维护性**：命名见名知意，核心逻辑必有注释，代码风格前后端统一
- **交付完整**：每次代码变更必须同步对应文档与 Git 提交信息，缺一不可
- **一致性对齐**：前后端接口规则、参数命名、数据格式严格对齐，禁止出现两端标准不一致的情况

## 二、公共交付规范（前后端通用，强制执行）

### 2.1 代码自测要求

- 开发完成必须验证主流程可正常运行，确保核心功能无阻断性问题
- 新增接口/功能必须验证三类场景：参数校验、正常流程、异常场景
- 修改已有代码必须验证原有功能不受影响，避免破坏性变更
- 前端修改必须验证样式还原、交互逻辑、不同尺寸下的布局兼容性
- 前后端联动功能必须完成联调验证，确保字段、格式、交互完全匹配

### 2.2 文档同步要求

- 新增/修改接口，必须同步更新「功能开发说明书.md」中的接口清单与字段说明
- 新增/修改表结构，必须同步更新数据库设计文档
- 新增/修改页面与交互，必须同步更新功能开发说明书中的交互说明
- 新增/修改公共组件，必须补充组件使用说明与 props 定义
- 变更配置项、部署方式，必须同步更新对应部署与配置文档

### 2.3 Git 提交规范

- 提交信息严格遵循约定式提交格式：`类型: 描述`
- 通用类型定义：
  - `feat`：新增功能、新特性
  - `fix`：修复 bug、问题
  - `style`：样式调整、格式修改，不影响业务逻辑
  - `docs`：文档更新、注释补充
  - `refactor`：代码重构，不改变功能逻辑
  - `config`：配置文件、工程脚本变更
- 描述简洁清晰，说明本次变更的核心内容，禁止模糊、无意义的提交信息

### 2.4 标准交付输出结构

每次代码交付必须严格遵循以下四部分结构，顺序不可调整，缺一不可：

1. **代码变更**：按文件路径分类列出所有修改/新增的代码，标注核心修改位置与函数名
2. **文档更新**：列出所有需要同步更新的文档路径与具体变更内容
3. **Git 提交建议**：给出符合规范的完整 commit message
4. **影响范围说明**：说明本次修改影响的模块、页面、接口，以及潜在风险点

## 三、前端开发专项规范

### 3.1 工程结构规范

#### 3.1.1 标准目录结构

前端统一采用分层目录管理，对应 `frontend/src/` 目录：

```
frontend/src/
├── views/        # 页面级组件，按业务模块划分
├── components/   # 公共可复用组件，与业务无关
├── api/          # 接口请求封装，按业务模块分文件
├── utils/        # 公共工具函数、通用方法
├── styles/       # 全局样式、主题变量、公共类
├── assets/       # 静态资源（图片、字体等）
├── router/       # 路由配置
└── store/        # 全局状态管理（按需使用）
```

#### 3.1.2 各目录职责边界

1. **views 页面层**
  - 仅负责页面级布局编排、业务数据组装，不封装通用UI元素
  - 禁止直接编写原生接口请求，统一调用 api 层方法
  - 一个页面对应一个路由地址，保持单一职责

2. **components 组件层**
  - 仅存放可复用的通用UI组件，禁止硬编码业务逻辑
  - 组件必须通过 props 接收数据，通过事件向外传递操作
  - 可按功能分类存放，如 `basic/` 基础组件、`business/` 业务通用组件

3. **api 接口层**
  - 所有后端接口请求统一在此封装，按业务模块拆分文件
  - 统一使用请求/响应拦截器，禁止页面内直接发起原生请求
  - 接口方法命名与后端接口对应，见名知意

#### 3.1.3 调用规则

- 调用方向：页面 → 组件 / api → 工具类，禁止反向依赖
- 公共组件禁止直接调用 api、访问路由，保持纯UI属性
- 工具类、全局样式可被所有层引用

### 3.2 组件与页面开发规范

#### 3.2.1 命名规则

- 页面组件、公共组件：大驼峰命名，文件名与组件名一致，如 `PptEditor.vue`
- 普通变量、方法：小驼峰命名，如 `slideList` `handleSave()`
- 常量：全大写+下划线，如 `MAX_SLIDE_COUNT`
- 路由路径：全小写，多单词用短横线分隔，如 `/ppt-editor`

#### 3.2.2 组件复用规则

- 基础交互组件（按钮、输入框、选择器、表单、表格、分页、弹窗、抽屉、提示、导航等）优先使用 Element Plus，禁止重复自研同类基础组件
- 业务组件应封装为 Element Plus 组件之上的业务组合，承载业务字段映射、状态编排和局部交互，不重新实现基础控件能力
- 同一UI元素在页面中出现 ≥ 2 次，必须抽取为公共组件
- 通用交互逻辑（如分页、弹窗确认）必须封装为通用组件/方法
- 公共组件必须定义清晰的 props 说明、事件回调，禁止内部硬编码业务字段
- 组件粒度适中，避免超大组件，也避免过度拆分增加维护成本

#### 3.2.3 页面开发规则

- 页面内只做业务编排，核心业务逻辑优先抽取到工具类或组合式函数中
- 数据加载、状态初始化必须放在对应生命周期钩子中，逻辑清晰
- 复杂页面按功能拆分为多个子组件，保持主页面代码简洁可读

### 3.3 接口请求规范（与后端严格对齐）

#### 3.3.1 请求基础规则

- 请求方法与操作严格对应：GET 查询、POST 新增、PUT 全量更新、DELETE 删除
- 接口路径与后端保持完全一致，统一前缀 `/api`
- Token 统一放置在请求头 `Authorization: Bearer xxx`，由拦截器自动注入
- GET 请求禁止携带 body，参数通过 query 传递
- 分页参数统一使用 `page`、`pageSize`，与后端约定完全一致
- 时间参数统一使用字符串格式 `yyyy-MM-dd HH:mm:ss`

#### 3.3.2 响应处理规则

- 统一使用响应拦截器解析后端标准返回结构 `{code, message, data}`
- 业务成功（code=200）直接返回 data 字段
- 业务失败统一弹出错误提示；401 状态自动跳转登录页
- 禁止在每个页面单独处理响应格式，必须走统一拦截逻辑

#### 3.3.3 异常处理

- 所有接口请求必须做异常捕获，避免页面白屏
- 请求失败必须给出明确的用户提示，禁止静默失败
- 核心操作（保存、生成、提交）必须添加加载状态，防止重复提交

### 3.4 样式与UI规范

#### 3.4.1 样式基准

- 统一使用 Element Plus 作为基础交互组件库，禁止私自引入其他 UI 组件库替代
- Tailwind CSS 仅用于布局、间距、响应式、自定义业务区块和少量业务视觉样式，禁止用 Tailwind 重复实现 Element Plus 已提供的按钮、表单、弹窗、表格等基础组件
- Element Plus 主题色、圆角等基础变量统一在 `frontend/src/styles/element/index.scss` 中维护，禁止组件内随意覆盖主题
- Material Symbols 与 Element Plus 图标搭配使用：Element Plus 图标优先用于组件库内置操作，Material Symbols 用于编辑器和业务语义补充

#### 3.4.2 样式命名与书写

- 推荐使用模块化样式或 BEM 风格，避免全局样式污染
- 类名全小写，多单词用短横线分隔，如 `.slide-item` `.tool-bar`
- 禁止使用 ID 选择器、标签选择器编写业务样式
- 布局优先使用 Flex / Grid，禁止大量使用浮动定位

#### 3.4.3 布局强制约定

- 按钮组默认水平排列，间距与全局规范保持一致
- 页面内边距、区块间距统一使用标准间距值，禁止随意写死像素
- 自适应场景优先使用相对单位，保证不同尺寸下布局一致性

### 3.5 代码编写规范

#### 3.5.1 注释规范

- 页面、核心公共组件必须添加功能说明注释
- 复杂业务逻辑、计算逻辑必须添加行内注释
- 公共工具方法必须说明功能、入参、返回值
- 禁止提交注释掉的废弃代码

#### 3.5.2 代码复用与解耦

- 相同逻辑出现 2 次及以上，必须抽取为公共方法或组件
- 禁止在组件内部复制粘贴大段重复代码
- 业务状态与UI视图分离，禁止在模板中编写复杂计算逻辑
- 固定配置、枚举值必须抽取为常量，禁止硬编码在业务代码中

#### 3.5.3 状态管理

- 全局共享数据才使用状态管理，页面内数据优先使用组件自身状态
- 禁止在组件内直接修改全局状态，必须通过官方方法更新
- 本地存储统一封装工具方法管理，禁止散落在各处直接操作

### 3.6 前端专项禁止行为

1. 禁止擅自修改接口字段、UI基准、组件库、全局样式变量
2. 禁止在页面内直接编写原生请求，禁止绕过 api 层调用接口
3. 禁止复制粘贴重复代码，通用元素必须抽取为公共组件
4. 禁止自研 Element Plus 已覆盖的基础按钮、输入框、表格、弹窗、抽屉、分页、消息提示等组件
5. 禁止硬编码色值、间距、业务常量，必须使用全局定义
6. 禁止擅自新增需求外的功能、交互、样式优化
7. 禁止擅自重构未要求修改的代码，禁止调整非本次范围的布局

## 四、后端开发专项规范

### 4.1 分层架构规范

#### 4.1.1 标准分层结构

后端统一采用三层架构，对应 `backend/src/` 目录：

```
backend/src/
├── controller   # 控制层：接收请求、参数校验、封装响应
├── service      # 业务层：业务逻辑、事务控制
│   └── impl     # 业务实现类
├── mapper       # 数据访问层：数据库读写
├── entity       # 数据库表对应实体
├── dto          # 请求入参、响应出参对象
├── common       # 公共工具、统一返回体、异常类、常量
└── config       # 项目配置、第三方组件配置
```

#### 4.1.2 各层职责边界

1. **Controller 控制层**
  - 仅接收请求、做基础参数校验、封装统一返回结果
  - 不编写业务逻辑，所有业务逻辑必须委托给 Service 层
  - 禁止直接调用 Mapper 操作数据库
  - 方法粒度与接口一一对应，一个接口对应一个 Controller 方法

2. **Service 业务层**
  - 承载全部业务逻辑，是事务控制的唯一层级
  - 负责业务校验、流程编排、数据组装
  - 仅调用 Mapper 层进行数据读写，不直接处理HTTP请求
  - 复杂业务可拆分为多个子方法，保持单一职责

3. **Mapper 数据访问层**
  - 仅负责数据库的增删改查操作，不包含任何业务逻辑
  - 单表操作优先使用框架自带方法，复杂查询自定义 SQL

#### 4.1.3 调用规则

- 调用方向只能从上到下：Controller → Service → Mapper，禁止反向调用
- Service 之间可互相调用，避免循环依赖
- 公共工具类、常量类可被所有层调用

### 4.2 接口开发规范

#### 4.2.1 RESTful 基础规则

1. **请求方法严格对应操作**
  - GET：查询数据，禁止 GET 请求携带 body 传参
  - POST：新增资源
  - PUT：全量更新资源
  - DELETE：删除资源

2. **路径命名规则**
  - 统一使用名词复数，禁止出现动词。正确：`/ppt-templates`，错误：`/getPptList`
  - 全小写，多单词用短横线 `-` 分隔
  - 多级资源采用路径嵌套，体现从属关系，如 `/users/{userId}/orders`
  - 路径参数占位符用 `{}` 包裹，如 `/ppt/{pptId}`
  - 所有业务接口统一前缀 `/api`

3. **核心 HTTP 状态码**
  - 200：查询/更新操作成功
  - 201：新增资源成功
  - 400：参数校验失败、请求格式错误
  - 401：未登录、Token 无效/过期
  - 403：已登录但无权限访问
  - 404：请求的资源不存在
  - 500：服务器内部未知错误

#### 4.2.2 统一响应体（强制）

所有接口必须使用以下固定结构，禁止自定义返回格式：

```json
{
  "code": 200,
  "message": "success",
  "data": null
}
```
- `code`：业务状态码，与 HTTP 状态码保持一致
- `message`：成功时固定为 `success`，失败时返回具体可读的错误原因
- `data`：响应数据，无数据时为 `null`
- 分页查询的 `data` 固定结构：`{ "list": [], "total": 0, "page": 1, "pageSize": 10 }`

#### 4.2.3 参数约定

- 分页参数统一命名：`page`（页码，从1开始）、`pageSize`（每页条数）
- 时间参数统一格式：`yyyy-MM-dd HH:mm:ss`
- 所有入参必须做非空、格式校验，校验失败返回 400
- Token 统一从请求头 `Authorization: Bearer xxx` 中解析

### 4.3 数据库开发规范

#### 4.3.1 命名规则

- 表名：小写+下划线，业务命名，如 `ppt_info` `user_record`
- 字段名：小写+下划线，禁止驼峰命名，禁止使用 SQL 关键字
- 布尔含义字段统一 `is_xxx` 命名，如 `is_deleted` `is_enabled`
- 普通索引：`idx_字段名`，多字段索引用下划线拼接；唯一索引：`uk_字段名`

#### 4.3.2 强制通用字段

所有业务表必须包含以下 3 个基础字段，禁止遗漏：

- `id`：bigint 类型，自增主键
- `create_time`：datetime 类型，创建时间，默认当前时间
- `update_time`：datetime 类型，更新时间，更新时自动刷新

#### 4.3.3 软删除规则

- 统一使用逻辑删除，字段为 `is_deleted`，tinyint 类型
- `0` 表示未删除，`1` 表示已删除，默认值为 `0`
- 所有查询接口默认过滤 `is_deleted = 0`，禁止物理删除业务数据
- 数据恢复操作仅需将 `is_deleted` 置为 0，禁止新增重复数据

#### 4.3.4 SQL 编写规则

- 禁止使用 `SELECT *`，必须明确指定查询的字段
- 禁止在循环中执行数据库查询，避免 N+1 问题，优先使用批量查询
- SQL 注释统一使用 `--` 符号
- 禁止字符串拼接 SQL，防止 SQL 注入
- 模糊查询禁止前置通配符（如 `%keyword`），避免索引失效
- 禁止在 SQL 中进行复杂业务计算，计算逻辑上浮到 Service 层

#### 4.3.5 事务管理

- 事务注解必须加在 Service 层的方法上，禁止加在 Controller 层
- 事务粒度要小，仅在需要数据一致性的多个写操作上添加事务
- 只读操作禁止添加事务，避免不必要的性能损耗

### 4.4 代码编写规范

#### 4.4.1 命名规范

- 类名：大驼峰命名，如 `PptService` `UserController`
- 方法名：小驼峰命名，动词开头，如 `generatePpt()` `getUserById()`
- 变量名：小驼峰命名，禁止歧义缩写，如 `pptTitle` `orderList`
- 常量：全大写+下划线分隔，如 `MAX_GENERATE_COUNT`
- 包名：全小写，多级包用点分隔

#### 4.4.2 注释规范

- Controller、Service 核心类必须添加类功能注释
- 公共方法、核心业务方法必须加注释，说明功能、入参、出参、异常场景
- 复杂业务逻辑、核心算法、易踩坑代码必须添加行内注释
- 自定义 SQL 必须添加功能注释，复杂查询需说明业务背景
- 禁止提交注释掉的废弃代码

#### 4.4.3 解耦与复用

- 单一职责原则：一个类/方法只负责一项功能，禁止编写超长万能方法
- 相同逻辑出现 2 次及以上，必须抽取为公共方法或工具类
- 业务状态、固定阈值必须定义为常量或枚举，禁止硬编码在代码中
- 第三方能力（AI 生成、文件存储、外部接口）必须封装为独立服务，禁止散落在业务代码中

### 4.5 异常与日志规范

- 必须使用全局异常处理器统一捕获所有异常，禁止 Controller 层手写 try-catch 封装返回体
- 业务异常抛出自定义业务异常类，系统异常统一返回 500 状态码
- 禁止将异常堆栈信息直接返回给前端
- 接口入口打印请求入参，出口打印响应结果与接口耗时，日志级别为 info
- 业务异常打印错误信息与入参，日志级别为 warn
- 系统异常、未知异常必须打印完整堆栈信息，日志级别为 error
- 禁止打印密码、Token 等敏感信息到日志中

### 4.6 后端专项禁止行为

1. 禁止擅自修改接口定义、表结构、分层架构
2. 禁止在 Controller 层编写业务逻辑、直接操作数据库
3. 禁止物理删除业务数据，禁止关闭软删除过滤
4. 禁止使用 `SELECT *`、循环查库、字符串拼接 SQL
5. 禁止硬编码业务参数、明文存储敏感信息
6. 禁止擅自重构未要求修改的代码、私自新增需求外功能

## 五、全局禁止行为红线（通用，绝对不能违反）

1. 所有变更必须严格对应需求范围，禁止自行新增任何需求未提及的功能、优化、重构
2. 禁止只交付代码，不同步更新文档、不提供 Git 提交信息
3. 禁止擅自修改全局技术栈、核心规范、设计基准
4. 禁止过度解读需求，存在歧义时必须先确认再开发
5. 禁止破坏项目整体分层架构与模块边界
6. 禁止提交存在明显安全隐患、数据泄露风险的代码

## 六、灵活放宽说明

可根据需求重要性分级执行：

- 核心功能、对外接口、公共组件、主流程页面必须严格遵守本规范
- 简单临时页面、内部工具方法、非核心辅助功能可适当放宽非核心注释与校验要求
- 索引命名精细化、多环境极致配置、非核心日志细节等扩展项，可随项目迭代逐步补充
- 规范优先级：数据一致性 > 接口契约 > 代码风格 > 注释细节
